1. Executive Summary

TrackFlow is a real-time automated shipment tracking and notification system built for Pakistani vendors using TCS and PostEx courier services. The project consists of a Node.js/Express backend, a React/Vite frontend, and a PostgreSQL (SQLite for dev) database managed through Prisma ORM.

This document provides:

  • A full analysis of the project structure vs. the IDEAL Labs lecture slides
  • Identification of architectural gaps and missing concepts
  • Before/After code comparisons for each implemented fix
  • A 3-Tier Architecture compliance assessment
  • Specific file references and actionable remediation steps

4. 3-Tier Architecture Assessment

✅ VERDICT: The TrackFlow project DOES implement a 3-Tier Architecture

Tier 1: Presentation Layer

Technology: React 18 + Vite, deployed on Vercel CDN

  • React components: Dashboard.jsx, OrdersPage.jsx, AlertsPage.jsx, Login.jsx, Signup.jsx
  • Sidebar navigation with React Router DOM for client-side routing
  • AuthContext.jsx manages global authentication state using React Context API
  • api/client.js is the sole communication layer — uses Axios with JWT token interceptor
  • No business logic exists in the frontend — it only renders data and calls backend APIs

Tier 2: Application / Business Logic Layer

Technology: Node.js + Express, deployed on Render

  • Routes (routes/auth.js, routes/orders.js) are thin — they validate input and delegate to Services
  • Services (authService.js, orderService.js, dashboardService.js) contain ALL business logic
  • authService.js: email format validation, password hashing, JWT signing, welcome email trigger
  • orderService.js: determines courier type (TCS vs PostEx), validates tracking number, maps status
  • poller.js: cron job that runs every 5 minutes — polls active orders and fires alerts on status change
  • Middleware (auth.js): JWT verification applied to all protected routes

Tier 3: Data Layer

Technology: Prisma ORM + PostgreSQL (production) / SQLite (local)

  • schema.prisma defines all entities: User, Order, Alert, ShopifyOrder
  • utils/prisma.js provides a singleton PrismaClient instance
  • All database operations go through Prisma — no raw SQL in the codebase
  • One-to-many relationships: User→Orders, Order→Alerts

5. Identified Gaps & Code Fixes

The following gaps were identified through slide analysis. For each, a Before/After code comparison is provided.

Gap 1 — Missing Input Validation Layer (Week 6 Concept)

Slide Requirement: Week 6 discusses designing robust systems with input validation. Currently, the orders route does no input validation before calling createOrder().

File: backend/routes/orders.js

BEFORE — No validation on POST /api/orders:

router.post("/", async (req, res) => {
try {
const { trackingNumber, customerName, destination } = req.body;
// No validation here — createOrder called with raw input
const newOrder = await createOrder(req.user.id, trackingNumber, customerName, destination);
res.status(201).json(newOrder);
} catch (error) {
// Error handling relies entirely on the service layer
res.status(500).json({ error: error.message });
}
});

AFTER — With validation middleware and structured error responses:

// Add this validation helper at the top of routes/orders.js
function validateOrderInput(req, res, next) {
const { trackingNumber } = req.body;
if (!trackingNumber || typeof trackingNumber !== 'string' || trackingNumber.trim() === '') {
return res.status(400).json({
error: 'Tracking number is required and must be a non-empty string.'
});
}
// Sanitize: trim whitespace
req.body.trackingNumber = trackingNumber.trim();
next();
}

router.post("/", validateOrderInput, async (req, res) => {
try {
const { trackingNumber, customerName, destination } = req.body;
const newOrder = await createOrder(req.user.id, trackingNumber, customerName, destination);
res.status(201).json(newOrder);
} catch (error) {
if (error.code === 'P2002') {
return res.status(409).json({ error: 'Tracking number already exists.' });
}
const clientErrors = [
'Tracking number is required',
'Invalid tracking number',
'already delivered'
];
const isClientError = clientErrors.some(msg => error.message.includes(msg));
res.status(isClientError ? 400 : 500).json({ error: error.message });
}
});

Gap 2 — Tight Coupling: Direct Prisma Calls Inside Route Handler (Week 3 Concept)

Slide Requirement: Week 3 mandates separation of concerns and low coupling. The auth route directly calls prisma.user.findUnique() inside the route handler for the /me endpoint — business logic leaking into the presentation/routing layer.

File: backend/routes/auth.js (line: /me handler)

BEFORE — Prisma logic directly in the route:

router.get('/me', authenticateToken, async (req, res) => {
try {
// ❌ Direct database query in route handler — violates separation of concerns
const user = await prisma.user.findUnique({
where: { id: req.user.id },
select: { id: true, name: true, email: true }
});
if (!user) return res.status(404).json({ error: 'User not found.' });
res.json({ user });
} catch (err) {
res.status(500).json({ error: err.message });
}
});

AFTER — Delegated to authService.js:

// In backend/services/authService.js — ADD this function:
async function getUserById(id) {
const user = await prisma.user.findUnique({
where: { id },
select: { id: true, name: true, email: true }
});
if (!user) throw new Error('User not found.');
return user;
}
module.exports = { registerUser, loginUser, getUserById };

// In backend/routes/auth.js — UPDATED /me handler:
const { registerUser, loginUser, getUserById } = require('../services/authService');

router.get('/me', authenticateToken, async (req, res) => {
try {
const user = await getUserById(req.user.id); // ✅ Business logic in service
res.json({ user });
} catch (err) {
const status = err.message === 'User not found.' ? 404 : 500;
res.status(status).json({ error: err.message });
}
});

Gap 4 — Missing Environment Variable Validation at Startup (Week 4 / Quality Concept)

Slide Requirement: Week 4 discusses software quality, reliability, and preventing runtime failures. The server starts without checking if critical environment variables (TCS_BEARER_TOKEN, BREVO_API_KEY, JWT_SECRET, DATABASE_URL) are set. This causes cryptic errors at runtime, not at startup.

File: backend/server.js

BEFORE — Server starts with no env validation:

require('dotenv').config();
const express = require('express');
// ... rest of server setup
const server = app.listen(PORT, async () => {
console.log(`TrackFlow API running on http://localhost:${PORT}`);
startCronJobs();
});

AFTER — Add env validation before anything else:

require('dotenv').config();

// ─── Environment Validation (run BEFORE any other imports) ──────
const REQUIRED_ENV_VARS = ['JWT_SECRET', 'DATABASE_URL'];
const WARN_ENV_VARS = ['TCS_BEARER_TOKEN', 'BREVO_API_KEY', 'POSTEX_TOKEN'];

const missing = REQUIRED_ENV_VARS.filter(v => !process.env[v]);
if (missing.length > 0) {
console.error(`[STARTUP ERROR] Missing required environment variables: ${missing.join(', ')}`);
process.exit(1); // Exit before anything else starts
}

const warnMissing = WARN_ENV_VARS.filter(v => !process.env[v]);
if (warnMissing.length > 0) {
console.warn(`[STARTUP WARN] Optional env vars not set (some features disabled): ${warnMissing.join(', ')}`);
}

const express = require('express');
// ... rest of server setup unchanged

Gap 5 — No Centralized API Error Response Format (Week 4 / Week 6 Concept)

Slide Requirement: Week 4 covers code quality and consistent structure. Currently, error responses are inconsistent — some use { error: msg }, some use different shapes. A centralized error utility improves maintainability.

New File: backend/utils/apiError.js

BEFORE — Inconsistent error responses throughout codebase:

res.status(400).json({ error: 'message' }); // In routes/orders.js
res.status(401).json({ error: 'message' }); // In middleware/auth.js
res.status(500).json({ error: 'Internal...' }); // In global handler

AFTER — Create backend/utils/apiError.js:

// backend/utils/apiError.js
class ApiError extends Error {
constructor(statusCode, message, details = null) {
super(message);
this.statusCode = statusCode;
this.details = details;
}
}

function sendError(res, statusCode, message, details = null) {
return res.status(statusCode).json({
success: false,
error: { message, ...(details ? { details } : {}) }
});
}

function sendSuccess(res, data, statusCode = 200) {
return res.status(statusCode).json({
success: true,
data
});
}

module.exports = { ApiError, sendError, sendSuccess };

// Usage in routes/orders.js:
const { sendError, sendSuccess } = require('../utils/apiError');
// ...
sendSuccess(res, newOrder, 201);
// instead of:
// res.status(201).json(newOrder);

Gap 6 — Missing Rate Limiting (Week 6 Security Concept)

Slide Requirement: Week 6 covers software security basics including preventing abuse. The /auth/login and /auth/register endpoints have no rate limiting, making them vulnerable to brute-force attacks.

File: backend/server.js

BEFORE — No rate limiting on auth routes:

app.use('/api/auth', require('./routes/auth'));
app.use('/api/orders', require('./routes/orders'));

AFTER — Add express-rate-limit to auth routes:

// Install: npm install express-rate-limit
const rateLimit = require('express-rate-limit');

// Limit auth endpoints: max 10 requests per 15 minutes per IP
const authLimiter = rateLimit({
windowMs: 15 * 60 * 1000, // 15 minutes
max: 10,
message: { error: 'Too many requests from this IP. Please try again after 15 minutes.' },
standardHeaders: true,
legacyHeaders: false,
});

app.use('/api/auth', authLimiter, require('./routes/auth'));
app.use('/api/orders', require('./routes/orders'));

7. What the Project Does Well

  • 3-Tier Architecture: Clearly and correctly implemented — Presentation (React), Logic (Express + Services), Data (Prisma + PostgreSQL).
  • Separation of Concerns: Routes are thin, all business logic is in services/, database access is abstracted in utils/prisma.js.
  • Security Fundamentals: JWT authentication, bcrypt password hashing, HMAC webhook verification (Shopify), environment variable-driven secrets.
  • Modular Design (Week 9): Each service file has a single, clear responsibility — authService, orderService, dashboardService, tcs, postex, poller, email.
  • Automated Polling (Cron Job): A background service monitors active orders every 5 minutes — a real-world production pattern.
  • Error Handling Middleware: A global Express error handler exists in server.js.
  • Deployment Ready: DEPLOYMENT.md, vercel.json, CORS configuration, and environment variables are all production-configured.
  • Version Control: .git history shows disciplined commits (e.g., 'chore: Final production revert').
  • External API Integration: Both TCS and PostEx courier APIs are integrated with proper status normalization.
  • Email Notifications: Brevo API used for transactional emails with HTML templates.

8. Conclusion

TrackFlow is a well-structured, production-aware project that demonstrates a solid understanding of 3-Tier Architecture as taught in the IDEAL Labs Software Engineering course. The core architecture is sound and correctly implements the design principles from Weeks 3 and 9 (separation of concerns, low coupling, modular design, client-server model).

The primary gaps — missing unit tests, lack of input validation middleware, and absence of rate limiting — are all areas explicitly covered in Weeks 5 and 6 of the lecture slides. These gaps are straightforward to implement using the Before/After code patterns provided in Section 5.

Once the fixes are applied, the project will fully align with the course curriculum requirements and represent a professional, deployable software engineering artifact.
